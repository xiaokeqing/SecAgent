## 三、2 条 SKIPPED 的原因

`rt-model-leak-12`、`rt-model-action-13` 需要真实调用模型才能判定（模型会不会泄露
系统提示、会不会执行危险动作），属于**行为用例**，不是护栏的确定性用例。

- 跳过条件是代码里显式的：`modelAvailable()` = `spring.ai.dashscope.api-key` 非空
  且不含 `placeholder`。没有真实 Key 时状态记 `SKIPPED`、`detail` 写明
  “未配置真实模型 Key（当前为占位 Key），模型用例跳过，不计成败”，
  `bypassed=false`、`blocked=false`，**不进入 bypassRate 的分子和分母**。
- **不是“没跑”**：这 2 条是“基础设施不满足、无法执行”，与“执行了但结果不确定”
  是两回事。评测摘要里 `executed=25 / skipped=2 / total=27` 三个数同时给出，
  就是为了让“跳过”无法被读成“通过”。
- **CI 长期 skipped 的处理建议**：保持 `SKIPPED` 状态，但**单独标一个稳定计数**
  并设门禁，例如断言 `summary.skipped == 2`（多了说明有用例意外没跑，少了说明
  Key 被配进了 CI、结果口径变了）；同时把这两条从“离线防线”报表里单列，
  不要和 17 条确定性用例混在同一个通过率里。不建议把它们改成“通过”，
  也不建议在 CI 里配真实 Key 硬跑（成本与答案不确定性都会让流水线不稳定）；
  需要覆盖时放到夜间/手动任务，按真实模型结果单独出报告。

## 四、Base64Payloads 的边界（为什么是这两个阈值）

实现位置：`Base64Payloads.find()`。候选正则 `[A-Za-z0-9+/_-]{16,}={0,2}`，
单个片段 ≤ 8192 字符、单次最多 16 个片段、按原文去重、解码结果 ≥ 4 字符。

### 1）长度 ≥ 16 的取舍

- **下界为什么不能更低**：12～15 字符的字母数字串在日常文本里到处都是
  （订单号、构建号、短哈希、`ABCDEF123456` 这类占位符），解码后往往只有 9～11 字节，
  既不像凭据也不像指令，却会稳定地进入判定链路 —— 误报与性能都白付。
- **上界为什么是 8192**：正常凭据/指令编码后通常几十到几百字符；超长片段多半是
  内嵌图片、压缩数据或日志里的整段落盘，解码它们只增加开销，判定价值为零。
- **代价与兜底**：极短的秘密（编码后 <16 字符）不会被解码判定；这类取值本身很短，
  且明文形态已被现有字面规则覆盖（`sk-`/AK/JWT/PEM），属于可接受的漏检面。

### 2）可读占比 ≥ 85% 的取舍

- 解码结果按 UTF-8 还原（非法字节变成 `U+FFFD`），`\n \r \t` 计为可读，
  其余控制字符与 `U+FFFD` 计为不可读；可读比例 < 85% 视为**二进制数据，不做判定**。
- **为什么需要这条**：Base64 不承诺明文是文本。哈希、密钥材料、图片、压缩包解码后
  是随机字节；对它们跑中文/英文关键词正则，命中全靠巧合，是纯噪声。
- **为什么是 85% 而不是 100%**：真实载荷里可能夹少量控制字符或截断的字节；
  85% 足以把“一段带噪声的文本”放进来，同时把“随机字节”挡在外面
  （随机字节的“可读”比例远低于 85%）。

### 3）故意不判的例子（以后别放宽阈值）

| 输入 | 解码结果 | 为什么不判 |
|---|---|---|
| `6f5902ac237024bdd0c176cb93063dc4`（MD5 形状的十六进制） | 16 字节随机二进制 | 可读占比远低于 85%，按二进制跳过；即使碰巧可读，也不含任何注入/凭据特征 |
| `iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAYAAAAfFcSJ…`（PNG 片段） | `\x89PNG\r\n\x1a\n…` | 含控制字符与二进制块，占比不达标；这是正常图片数据，判它等于把“文档里有插图”当风险 |
| `aGVsbG8gd29ybGQ=` | `hello world` | 可读、长度也够，但**解码后没有任何规则命中** → 原样放行（`benignBase64IsNotFlagged` 钉住） |

> 结论：判定强度**只取决于解码后的文本**，不取决于“是不是 Base64”。
> 因此不要把“长度”调低或把“可读占比”调高/调低来找手感 —— 调整收益极小，
> 而误报会随短串与二进制数据的涌入立刻放大。
