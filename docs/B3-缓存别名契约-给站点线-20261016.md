## 1. 为什么要有别名（实测，不是推测）

Cloudflare **按 URL 扩展名**决定默认是否缓存。本 zone 实测（同一 zone，两次请求取第二次状态）：

| 路径 | origin 的 `Cache-Control` | `cf-cache-status` |
|---|---|---|
| `/robots.txt` | public, max-age=14400 | **HIT** |
| `/js/kurisu-player.js` | public, max-age=14400 | **HIT** |
| `/index.json` | public, max-age=300 | **DYNAMIC** |
| `/kurisu/manifest.json` | public, max-age=2592000 | **DYNAMIC** |
| `/sitemap.xml` | public, max-age=300 | **DYNAMIC** |

⇒ **`.js` / `.txt` 命中默认缓存列表；`.json` / `.xml` 不命中**（即使 origin 已给正数 max-age）。
而 `/api/public/alerts` 这种**无扩展名**路径必然 `DYNAMIC`、每次回源 —— 这就是"后端本机 3~5ms、
经 CF 却要 0.94~2.6s、页面并发 7~9 个端点 ≈ 十几秒"的全部原因。

**所以：别名是"给同一个 payload 换一个可被边缘缓存的后缀"**，不是一个新接口。

## 3. 响应头契约

| 头 | 别名路径 | 旧路径（未变） |
|---|---|---|
| `Cache-Control` | **`public, max-age=45, stale-while-revalidate=90`** | `public, max-age=15` |
| `Access-Control-Allow-Origin` | **`*`** | 白名单来源**精确回显**，非白名单不下发 |
| `Vary` | **无** | `Origin` |
| `X-Content-Type-Options` | **`nosniff`** | 无 |
| `Content-Type` | `application/json`（**不是** JS，别按脚本执行） | 同左 |
| `Access-Control-Expose-Headers` | 旧集合 **+ `Age`** | 旧集合 |
| `ETag` | **按"数据内容"算的稳定值**（同一快照窗口内不变；见 §3.3） | 按完整响应体算（原样） |
| `X-Data-Source` / `X-RateLimit-*` | 保留 | 保留 |

### 3.1 为什么别名 TTL 是 45 秒 + `stale-while-revalidate=90`

站点 `/alerts/` **每 40 秒轮询一次**（`layouts/partials/xk-demo/api-bind.html:41` `REFRESH = 40000`
配 `:1003 setInterval(load, REFRESH)`）。边缘 TTL 必须**长于轮询间隔**，否则：

| 边缘 TTL | 每次轮询的结果 | 源站请求量（9 端点） |
|---|---|---|
| 15s（= 应用内快照 TTL） | **每次都过期** → 每次轮询 9 次再验证 | 9/40s ≈ **13.5/分**（逼近每 IP 20/分 上限） |
| **45s** | 落在 TTL 内 → **命中边缘缓存、零回源** | ≈ 9/85s ≈ **6.4/分** |

`stale-while-revalidate` 的作用：即使再验证发生，边缘也**先把手上那份发出去**、后台再去源站确认
⇒ 用户侧不会被"回源 + TLS + 边缘选择（实测曾命中 LHR 伦敦）"卡住。这正是"加载很慢"的直接解药。

**代价（如实写）**：数据最旧 45 秒。页面必须用 `snapshotAt` + `Age` 如实显示（§4），
不许因为被缓存而假装更新（红线 D4）。

### 3.2 ★实测发现：浏览器侧 TTL 被 Cloudflare 改写成 4 小时

同一路径同时测 origin 与 CF（2026-10-16 20:08，srv1）：

| 取数路径 | `Cache-Control` |
|---|---|
| 本机直连 origin `http://127.0.0.1:9900/api/public/alerts.js` | `public, max-age=15` ← 代码里的值 |
| 经 CF `https://demo.xiaokeqing.cn/api/public/alerts.js` | **`public, max-age=14400`** ← 被改写了 |

⇒ 这是 zone 的 **Browser Cache TTL**（4 小时）覆写：CF 会把较短的 `max-age` 抬到该设置值。
**后果**：浏览器可能把这份数据缓存 4 小时（第二次打开页面会看到旧数据）。

**两条处理（建议都做）**：
1. **站点线**：前端取数走**条件请求**（或保留 `cache:"no-store"` 语义），不依赖浏览器缓存 ⇒
   每次都问 CF（CF 命中则毫秒返回）。**这就是 B2 那批要做的事。**
2. **站主**：CF 控制台 → Caching → **Browser Cache TTL 改为 "Respect Existing Headers"**
   （我们改不了：`.cf-token` 已失效，CF API 返回 401）。

### 3.3 为什么别名 ETag 必须按"内容"算（否则边缘缓存等于没做）

`PublicEtagFilter` 默认按**完整响应体**算 ETag，而别名响应体里的 `cacheAgeSeconds` 每秒都在变。
实测（同一快照窗口、`data` 完全相同）：

```
try1  ETag="bed95db50d38e108fd4f47e…"  snapshotAt/cacheAge=2026-10-16T20:08:19+08:00 9
try2  ETag="194d6cb3a41862c28c4c118…"  snapshotAt/cacheAge=2026-10-16T20:08:19+08:00 12
顶层键差异: ['cacheAgeSeconds']   data 内部差异: []
```

⇒ ETag 每次都变 ⇒ CF 的再验证**永远拿不到 304** ⇒ 每次过期都是一次完整的 200 回源。
现在别名 ETag **只对 `data` 内容算**（键排序后哈希，剔除 `snapshotAt`/`cacheAgeSeconds` 这类
每请求都变的元数据），过滤器遇到预置 ETag 就沿用 ⇒ **同一快照窗口内 ETag 稳定、再验证可 304**。
回归用例：`PublicApiCacheAliasTest.aliasEtagIsStableWithinSnapshotWindow`、
`PublicEtagFilterTest.presetEtagWins`。

**为什么别名可以 `*` 且去掉 `Vary`**：实测同一端点在
`https://xiaokeqing.cn` / `https://www.xiaokeqing.cn` / `https://example.com` / 无 `Origin`
四种情形下，响应体**逐字节一致**（把秒级 `generatedAt` 这类时间字段剔除后比对；`kb` 的
四来源差异经定性确认**只来自 `generatedAt` 秒级时间戳**）⇒ 载荷里没有随来源变化的东西。
代价：别名放弃了"浏览器侧白名单"这层限制（数据本来也是公开只读的，`curl` 一直能读）；旧路径仍然严格白名单。

## 4. 新鲜度语义（★这条是红线：被缓存 ≠ 可以假装更新）

别名响应体**多四个顶层字段**（旧路径**没有**，所以旧路径逐字节不变）：

```jsonc
{
  "code": 200, "message": "success",
  "data": { /* ……与旧路径完全一致…… */ },
  "snapshotAt": "2026-10-16T19:38:12+08:00",  // 本响应体内数据的"真实生成时刻"
  "cacheAgeSeconds": 0,                        // 生成这个响应体时，数据已经有多旧
  "snapshotTtlSeconds": 15,                    // 应用内快照 TTL（= Cache-Control max-age）
  "freshnessNote": "……口径说明，人读的……"
}
```

**前端显示规则（务必照做）**：

1. 页面上的"刚刚同步 / 数据时间"**必须**用 `snapshotAt` 渲染 —— **不许**用"收到响应的时刻"，
   也不许用 `Date.now()`（那正是"被缓存后假装更新"）。
2. 想显示"这份数据有多旧"时：**真实年龄 = `cacheAgeSeconds` + 响应头 `Age`**。
   `Age` 是 Cloudflare/中间缓存放的时间，它**不在** CORS 安全列表里，所以后端已在
   `Access-Control-Expose-Headers` 中放行（别名路径专属），跨域下 JS 才读得到。
3. `data.generatedAt` 保持原语义（各端点自己的口径）；**页面统一以 `snapshotAt` 为准**，
   这样同一个 15 秒窗口内显示不会跳动。

## 5. 前端改造清单（站点线执行）

1. 把 7~9 个 `fetch(apiBase + '/api/public/<name>')` 改成 `'/api/public/<name>.js'`。
2. 解析方式不用改：**继续 `res.json()`**（`Content-Type` 仍是 `application/json`；`Response.json()`
   与 Content-Type 无关）。
3. ⚠️ **禁止给这些地址加 cache-buster**（`?cb=…`、`?t=…`、`Date.now()`）：那会让 Cloudflare
   每次都当作新 URL ⇒ 100% 回源，等于白做。（查询参数本身是允许的，比如 `kb.js?q=口令`、
   `story.js?src=…`；禁止的是"每次随机"的参数。）
4. 超时/重试/保留上次成功数据由站点线那批（B2）负责；**建议顺序**：先取 `.js`，失败再回落旧路径（可选，做兜底更稳）。
5. `Age` 想读就读（已放行）；读不到时退化成"只显示 `snapshotAt`"也是可接受的降级。

## 6. 验收方法（站点线可复跑，用 `cf-cache-status` 当判据）

```bash
# ① 冷 + 热两次，第二次应为 HIT（别用"两次响应体逐字节相同"当判据：时间字段必然变）
curl -s -o /dev/null -D - "https://demo.xiaokeqing.cn/api/public/alerts.js" | grep -i 'cf-cache-status'
curl -s -o /dev/null -D - "https://demo.xiaokeqing.cn/api/public/alerts.js" | grep -i 'cf-cache-status\|^age:'
# ② 新鲜度字段存在且随快照走
curl -s "https://demo.xiaokeqing.cn/api/public/alerts.js" | python -c "import json,sys;d=json.load(sys.stdin);print(d['snapshotAt'], d['cacheAgeSeconds'], d['snapshotTtlSeconds'])"
# ③ 旧路径一个字没变（应无 snapshotAt，且有 Vary: Origin）
curl -s -D - "https://demo.xiaokeqing.cn/api/public/alerts" -H 'Origin: https://xiaokeqing.cn' | grep -iE 'vary|access-control-allow-origin'
```

目标：`cf-cache-status: HIT`（或 `REVALIDATED`）且**经 CF 的 P95 ≤1.5s**（≥10 次采样）。

## 7. 已知限制（照实写）

- **`ETag` 口径**：`PublicEtagFilter` 按**完整响应体**算 SHA-256（前 16 字节）。
  7 个走快照的端点（overview/alerts/honeypot/audit/latest/geo/webstats）在 15 秒窗口内响应体稳定
  ⇒ ETag 稳定 ⇒ 条件请求（304）有效；而 `kb`/`story` 体内 `generatedAt` 精确到秒 ⇒ **它们的 ETag 每秒都变
  ⇒ 304 基本不命中**（代价是每次重新传 ~0.6KB，不是正确性问题）。要收口这条需与"时间字段口径"同批改，
  属独立批次，未做。
- `/api/public/alerts/{aggId}`、`POST /ask`、`POST /tts` **没有别名**（见 §2）。
- 本文只解决"边缘能不能缓存"。**CF 侧 Cache Rule**（更干净的方案 A）因 `E:\DeepSeek1\work\.cf-token`
  已失效（CF API 返回 401，三处文档均有记录）而无法实施，需要站主重发一枚带 `Zone:Cache Rules:Edit` 的 token。
