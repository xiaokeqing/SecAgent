## 1. 为什么会回显（事件成因）

一次运维命令把 Wazuh indexer 的凭据带进了会话日志。口令进日志的典型路径有三条，本项目三条都踩过：

1. **命令行参数回显**：`curl -u admin:<口令>`、`grep <口令>`、`awk -v a=<口令>` ——
   参数会进 `ps`、shell history，以及 **sudo 审计日志 `/var/log/secure`**。
   ▶ 本轮实测复现了这条路径：我用指纹前缀做全盘检索时，`/var/log/secure` 把
   `COMMAND=... grep ... <前缀>` **连同参数整条记了下来**。这就是"凭据进 argv 就会落盘"的活证据。
2. **管道/工具输出回显**：`set -x`、把含密钥的行打进终端。
3. **应用日志回显**：`/var/log/secagent/app.log` 里存在 `用户=<x> 口令=<y>` 形态的
   高危告警通知文本（蜜罐抓到的攻击者凭据），实测 **567 处**。内容是攻击者口令而非我方密钥，
   但证明**这条日志管道会原样保存凭据**（详见 `docs/安全建议-应用日志凭据脱敏评估.md`）。

### 1.1 上一轮实施把 srv2 跑成死循环（必须记住的教训）

上一轮用 `awk -v a=<口令>` 做「把口令替换成 `<IDX_PW>`」的脱敏管道，
**替换模式被传成了空字符串**：

- `index(rest, "")` 在 awk 中**恒为真**（空串是所有字符串的子串）→ `while` 条件永远成立；
- 每次循环把结果拼回 `rest` → 字符串无上限增长 → RSS 爬到 **1.58GB**、CPU 100%；
- 宿主可用内存被压到 **113MB**，大量 swap；杀掉整条父链后恢复到 1877MB。

本轮全程遵守的硬约束：

| # | 约束 | 落实方式 |
|---|---|---|
| ① | 绝不用变量拼「替换模式/正则/awk -v 参数」 | 全程零 awk/sed 脱敏管道；文件改写一律用 python 按行处理 |
| ② | 任何一次性文本处理必须带 `timeout` | 所有远端 grep/find/curl 都带 `timeout` |
| ③ | 不让含密钥的输出经过手 | 只打印长度 + sha256 前 8 位；明文从不离开服务器 |
| ④ | 不确定会不会死循环就别跑 | 未引入任何驻留/长跑的新命令 |

**指纹算法必须统一**：`printf '%s' "$v" | sha256sum` 与 `echo "$v" | sha256sum` 结果**不同**
（后者多一个换行）。本轮曾因此误判「容器口令与 .env 不一致」。统一为 `printf '%s'` 后一致。
**结论：指纹算法不统一 = 自造假故障。**

## 6. 为什么没有轮换 admin（方案 B 仍待决）

`filebeat` 用**同一个 admin 口令**把告警**写入** `wazuh-alerts-*`。
改 indexer 侧口令而不同步 filebeat ⇒ **告警写入立刻 401 中断**；
同步 filebeat 就必须**重启 filebeat**（`analysisd`/`logcollector` 不受影响，但写入有短暂窗口）。
按决定，此事需用户拍板维护窗口，故**本次未做**。

另：任务原口径「旧口令失效」需更正 —— 线上真口令是 `sha256:dc056974`(len=20)，
而 `admin:SecretPassword`（默认口令）**早已 401**，不能拿它当"轮换有效"的证据。

### 6.1 方案 B 的步骤（备好待用）

1. 备份 `internal_users.yml`、`filebeat.yml`。
2. `hash.sh -env` 生成 admin 新哈希 → 写入 `internal_users.yml` → `securityadmin.sh -f -t internalusers`。
3. 更新 `filebeat.yml` 的口令 → **重启 filebeat**（`analysisd`/`logcollector` 不动）。
4. 验证：告警写入恢复实时（<60s）、`filebeat` 无 401、admin 旧口令 401 / 新口令 200。

### 6.2 一个持久化缺口（与方案 B 相关的风险）

`secagent_ro` 已写入 bind-mount 的 `internal_users.yml`，**容器重启不丢**。
但 **`roles.yml` / `roles_mapping.yml` 未挂载**：若将来有人对这两个文件执行
`securityadmin.sh -f`（例如镜像升级后按官方文档重放配置），`secagent_alerts_ro` 角色**可能被覆盖丢失**。
**建议**：把 `role-secagent_alerts_ro.json` 纳入配置版本化管理（RUNBOOK §6.6 已有同类机制），
并在任何 `roles.yml` 重放之前，先确认 security 索引里 `secagent_alerts_ro` 仍在。
