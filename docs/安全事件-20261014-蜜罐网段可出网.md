# 安全事件记录：蜜罐网段可出网（2026-10-14 发现并修复）

> 记录人：集成方（夜间自主推进会话）｜ 发现人：蜜罐升级实施方（在部署 Dionaea 前的侦察阶段）
> 位置：srv2（腾讯云）`DOCKER-USER` 链 ｜ 状态：**已修复并四类验证**（2026-10-14 01:0x CST）

## 一、事实

`DOCKER-USER` 链里，8 条**按目的端口**放行、**不限定来源**的规则排在那条"蜜罐网段出网丢弃"规则**之前**：

```
（修前，行号为 iptables -S DOCKER-USER 的输出序号）
 2..9  -A DOCKER-USER -p tcp -m tcp --dport {23,21,27017,1433,8443,8080,6379,3306} -j ACCEPT
10      -A DOCKER-USER -s 172.19.0.0/16 -m state --state RELATED,ESTABLISHED -j ACCEPT
11      -A DOCKER-USER -s 172.19.0.0/16 -d 127.0.0.11/32 -j ACCEPT
12      -A DOCKER-USER -s 172.19.0.0/16 -j DROP
```

因为 iptables 是**首条匹配即生效**，蜜罐网段（`172.19.0.0/16`，Cowrie / secagent-decoy 所在网络）发往
任意主机 21/23/1433/3306/6379/8080/8443/27017 的流量在第 2–9 条就被 ACCEPT，**根本走不到第 12 条的 DROP**。

**影响**：蜜罐一旦被攻陷，攻击者可把它当**跳板**对外发起（限这 8 个目的端口的）连接 ——
这直接违反"蜜罐被拿下也不能当跳板"的设计前提。

### 一.1 影响窗口（从什么时候开始的）

用"洞出现之前的那份 iptables 快照"来定界（不靠推测）：

```

  → 该文件里 DOCKER-USER 只有三条（RELATED,ESTABLISHED / DNS / DROP），**没有任何 --dport 放行**
  → 也就是说 10:02:24 时洞【还不存在】
· 诱饵容器 secagent-decoy 创建于 2026-10-13T02:25:39Z = 10:25:39 (+08)
  → 那 8 条放行规则是 srv2-decoy-ports.sh --apply 加的，且当时用 `-I DOCKER-USER 1`
    插到了 DROP 之前 —— 洞就是这一刻出现的

```

**窗口 ≈ 2026-10-13 10:25 → 2026-10-14 01:0x（+08），约 14.5 小时。**
这段窗口存在的前提是"诱饵脚本用 -I 把放行插到链首"——同一天 23:00 更新脚本副本时没有改这一点，

· 集成方独立复核：在 srv2 上 `iptables -S DOCKER-USER`，确认 DROP 在第 12 行、8 条 ACCEPT 在第 2–9 行

## 三、修复（集成方执行）

```
1) 备份：/root/iptables-backup-20261014-005131.rules（272 行）
2) 重排为正确顺序：
     -s 172.19.0.0/16 -m state --state RELATED,ESTABLISHED -j ACCEPT   ← 回程流量，必须在 DROP 之前
     -s 172.19.0.0/16 -d 127.0.0.11/32 -j ACCEPT                      ← 容器 DNS，必须在 DROP 之前
     -s 172.19.0.0/16 -j DROP                                        ← ★ 提到这两条之后
     --dport {21,23,1433,3306,6379,8080,8443,27017} -j ACCEPT         ← 移到 DROP 之后
       （这 8 条是给**外部连进来**用的：入向的源不是蜜罐网段，所以放在 DROP 之后仍然有效）
3) 落盘：/etc/iptables/rules.v4（既有 `secagent-firewall-restore.service` 就是
   `iptables-restore -n < /etc/iptables/rules.v4`，因此**重启后会重建出新顺序，洞不会回来**）；
   另存一份 /etc/secagent/iptables-post-dionaea.rules 备用
```

## 四、纠正一条错误记录（重要）

此前 RUNBOOK / 交付说明里写过"蜜罐网段 **egress DROP intact**"（作为隔离有效的证据）。
**这句是错的** —— DROP 规则确实存在，但被前序 ACCEPT 规则旁路，实际并未生效。
本次事件后，凡涉及隔离的结论**必须以"主动外连实测失败"为证据**，不接受"我配了 DROP 规则"这种表述。

## 五、遗留问题 —— 2026-10-14 01:1x 已核实/已补（下面每条都给了方法与结论）

### 5.1 这期间有没有**真实的**蜜罐外连成功记录？→ **没查到**（三个面都查了）

| 查什么 | 怎么查 | 结果 |
|---|---|---|
| Suricata 流事件里源是蜜罐网段 | `grep -c '"src_ip":"172.19\.' /opt/suricata/logs/eve.json` | **0 条**（整份 4.2 亿字节的 eve.json） |
| Suricata 里"从本机发起、打到那 8 个端口"的流 | `grep '"src_ip":"10.0.0.10"' <eve>` 再按 `dest_port` 过滤 | 命中 3306×1 / 8080×4，但逐条看原文是多宿主环境下的零星流量，**无法证明来自蜜罐容器**；1433×31 同样是对外流量统计、不是蜜罐出向 |
| Wazuh 里的"跳板/egress"类告警 | 在 alerts.json 里搜这两个词 | **0 条**（而且本来也没有规则覆盖"蜜罐出向"，所以"没有告警"不能作为"没发生"的证据） |
| 当前连接跟踪 | 没有 `conntrack` 命令 | 未能查 |

**结论：没有查到实际成功外连的记录。** 但要说清这只能说明"没记录到"：
Suricata 抓的是 eth0 上**经 SNAT 之后**的包（源已变成 10.0.0.10），蜜罐容器的出向流量
与宿主自身的出向流量在抓包层面**长得一样**，所以"从 10.0.0.10 出去"这件事本身不能区分是谁发的。
真要区分，需要在 DOCKER-USER 上给出向流量单独打日志（本次没做）。
另外诱饵容器本身只是 `nc -l`（从不主动外连）、Cowrie 也没有出向行为，
所以**从行为上看更可能是"能力存在但未被利用"** —— 这只是推断，不是证据。

### 5.2 端口移交后重跑 A/C 验证 + append 445 → **已完成**

```
· 移交：1433/3306 从 secagent-decoy 转给 Dionaea（诱饵保留 21/23/6379/8080/8443/27017）
        顺序是"先缩诱饵的端口映射，再起 Dionaea"（反了会端口冲突）
· 445：用 `iptables -A`（**只追加到链尾**，在 DROP 之后）放行 + ufw allow 445/tcp，
        随后 iptables-save > /etc/iptables/rules.v4（旧文件已另存备份）
· A 类（容器内主动外连）重跑：9 个端口（21/23/445/1433/3306/6379/8080/8443/27017）
        逐个尝试连 8.8.8.8 → 全部 timeout；eth0 抓包 **SYN 全为 0**
        对照组（同一镜像、默认网桥、连 31.13.94.41:443）→ eth0 抓到 **SYN=3**
        → 证明"0"是隔离造成的，不是路径不通
· C 类（外部连入）重跑：从 srv1（47.96.106.187，另一台机器）打 3306
        → 收到真实 MySQL 握手：34 00 00 00 0a 35 2e 37 2e 31 36 = 版本 "5.7.16"（Dionaea）
        打 1433 → 收到真实 TDS prelogin 响应（04 01 00 2b ...）
        诱饵的 21/23/6379/8080/8443/27017 仍能握手 → 入向没被误伤
· 顺序自检：当前 DOCKER-USER 里 DROP 在第 4 行、端口放行从第 5 行起 → 正确

【注意】445 虽然主机侧放行了，但**腾讯云安全组还没放行**（从 srv1 连 445 仍 timeout）。
要让公网扫到 SMB，需要在控制台放行 445/tcp —— 这一步只能站主做。
```
