# 安全建议：凭据进入「应用日志」与「公开响应」的评估（2026-10-14）

> **本文档只做评估，未实施任何改动。** 评估对象是蜜罐（Cowrie/Dionaea）抓到的
> **攻击者**登录凭据在本项目内部的流转与落盘。
> 结论分两部分：**① 日志卫生（内部）** 与 **② 公开响应（对外，优先级更高）**。
> 本文件不含我方任何口令；出现的"口令"值均为攻击者提交的字符串。

| # | 问题 | 面 | 严重度 | 状态 |
|---|---|---|---|---|
| ① | `口令=<明文>` 落进 `/var/log/secagent/app.log` | **内部** | 中（日志卫生） | 仅评估 |
| ② | 同样的 `口令=<明文>` 也落进 `data/notify-audit.jsonl` | **内部** | 中（日志卫生） | 仅评估 |

### 0.1 关于 ③ 的重要更正（避免误判）

**`/api/public/honeypot` 是干净的**（稳定输出 `口令=[口令已隐藏]`），
RUNBOOK **§27.4 记录的那次修复是真实有效的**。
漏网的是**另一条代码路径**：`/api/public/alerts`。

而且 ③ 是**间歇性**的 —— 只在取数窗口（5 分钟）内恰好出现"蜜罐登录成功"告警时才可见。
90 秒实测抽样 **2/9 命中**：

```
sampling /api/public/alerts every 10s for 90s ...
  [ 10s] clean
  ...
  [ 80s] ★ LEAK: 口令=<明文> 来源=103.149.197.34
  [ 90s] ★ LEAK: 口令=<明文> 来源=103.149.197.34
leak observations: 2 / 9 samples
```

> ⚠️ **正因为它间歇出现，单次 `curl | grep` 很可能"看着是干净的"而误判为已修复。**
> 验证必须**持续抽样**，或直接按下面的复现命令把窗口放大。

原始实测样本（2026-10-14 01:56 UTC）：

```
GET http://127.0.0.1:9900/api/public/alerts
  "title":    "蜜罐: 攻击者\"登录成功\" 用户=root 口令=<明文> 来源=103.149.197.34"
  "ruleName": "蜜罐: 攻击者\"登录成功\" 用户=root 口令=<明文> 来源=103.149.197.34"
```

> 澄清：泄露的是**攻击者猜的口令**，不是我方密钥；因此**不构成我方凭据泄露**。
> 但公网可读到"蜜罐实时账号口令对"本身即不良实践，且与项目自述红线矛盾，属**对外缺陷**。

## 2. 根因（精确到行为，不只是"没脱敏"）

### 2.1 数据来路（应用主动透传未脱敏原文）

Wazuh 规则 100102 把攻击者提交的账号口令**写进了 `rule.description`**：

```
100102 蜜罐: 攻击者"登录成功" 用户=<u> 口令=<p> 来源=<ip>
```

应用侧正则抽值并**原样**放进通知/告警标题：

| 位置 | 内容 |
|---|---|
| `WazuhService.java:342-343` | `RE_CRED = Pattern.compile("用户=(\\S+)\\s+口令=(\\S+)")` |
| `WazuhService.java:403` | `mCred = RE_CRED.matcher(desc)` |
| **`WazuhService.java:349`** | **注释：`蜜罐战报：…（返回未脱敏值，掩码在公网边界做）`** |

→ 设计是"源头保持原文，**边界**负责打码"。所以问题不在取数，而在**边界有洞**。

### 2.2 边界为什么有洞（关键）

公开 GET 的统一出口是 `ok()`，它调用 `ship()`：

```java
// PublicApiController.java:1204-1214  ok()
body.put("data", ship(data));            // ← 所有公开 GET 都过这里

// PublicApiController.java:132-141  ship()
data.forEach((k, v) -> out.put(k, scrubDeep(v)));

// PublicApiController.java:143-146  scrubDeep()
if (v instanceof String s) {
    return assets().scrub(s);            // ★ 只调用了【资产名过滤器】
}
```

**`scrubDeep()` 只调用 `assets().scrub(...)`（资产名停用词），完全没有调用凭据脱敏。**
于是：

- `PublicOutputGuard` 里那条**中文口令规则**
  （`Pattern.compile("(?i)(口令|密码)\\s*[:=：]\\s*\\S+")`，`PublicOutputGuard.java:76`，
  §27.4 明确说这个规则是为本次场景加的）**在这条路径上不会被触发**；
- `CredentialStructure.hidePasswords()` 只被 `/honeypot` 与公开问答/审计路径**显式**调用：

```java
PublicApiController.java:844   m.put("reason", policy.displayText(CredentialStructure.hidePasswords(...)));
PublicApiController.java:915   x.put("detail", policy.displayText(CredentialStructure.hidePasswords(...)));  // /honeypot timeline
PublicAuditReader.java:102     m.put("reason", CredentialStructure.hidePasswords(text(n, "reason")));
```

- 而 `/alerts` 的构造 `buildAlerts()`（`PublicApiController.java:952-992`）
  直接 `publicList.add(publicAggregate(g))` 后 `return data;`，
  **没有任何一处调用 `hidePasswords()`**。

**结论**：`/honeypot` 走了"显式调用 `hidePasswords`"，`/alerts` 只走了"通用 `ship()`"，
而 `ship()` 里没有凭据脱敏 → **同一类泄露在 alers 路径上完好无损。**
这也解释了 §27.4 的自测为什么没抓到：它的自测清单是 `latest alerts honeypot audit`
（§27.5），但当时若窗口内没有蜜罐登录成功告警，`alerts` 一行就会**假通过**。

### 2.3 落进日志的两个点（①②）

| # | 文件:行 | 语句 | 输出 |
|---|---|---|---|
| ① | `NotificationAudit.java:120` | `logger.info("通知审计 outcome={} reason={} event={}", outcome, reason, event)` | `NotifyEvent.toString()` → `title=` 含明文口令 |
| ② | `NotificationService.java:466` | `logger.info("通知已发出：{}（…）", event.title(), …)` | `event.title()` → 明文口令 |

`NotifyEvent.toString()`（`NotifyEvent.java:197-200`）直接拼 `title`，**不脱敏**。

> **同一文件里的自相矛盾（最省力的证据）**：`NotificationAudit` 对 **IP** 做了 `maskIp()`
> （`NotificationAudit.java:129-144`，审计里存 `targetIpMasked`），**却把口令原样写入**。
> "IP 要打码、口令不用" —— 明显是疏漏，不是有意取舍。

## 3. 建议改法（每次都选用已有的脱敏设施，不新造启发式）

### 3.1 治 ③（对外，优先）—— 2 行

在 `buildAlerts()` 里把标题过一遍**已有**的 `hidePasswords`，与 `/honeypot` 完全一致：

```java
// PublicApiController.java buildAlerts() 内，publicList.add(publicAggregate(g)) 之后
publicList.add(CredentialStructure.hidePasswords(publicAggregate(g)));
```

或更彻底（一次覆盖全部公开 GET，含未来新增端点），在 `scrubDeep()` 里补上凭据脱敏：

```java
// PublicApiController.java:143-146
if (v instanceof String s) {
    return CredentialStructure.hidePasswords(assets().scrub(s));   // ★ 资产名 + 口令 两道
}
```

> 两种都"复用已有设施"。推荐**第二种**：它把"口令永不公开"变成 `ship()` 出口的**结构性保证**，
> 而不是要求每个新端点作者记得手动调用 —— 本次漏洞正是"靠人记得"导致的。
> 代价：`scrubDeep` 会遍历公开响应里所有字符串，需注意 `hidePasswords` 的正则开销
> （对 99 条告警的小载荷可忽略；建议改后压一次 `/api/public/alerts` 的 P95 确认）。

**不要**只调长度阈值或往关键词表加英文词 —— §2.2 已证明问题是**调用点缺失**，不是规则不够宽。

### 3.2 治 ①②（内部日志/审计）

1. `NotificationAudit.record()`：`row.put("title", …)` 与那行 `logger.info` 都改用
   `CredentialStructure.hidePasswords(event.title())`（该类已 import 同包工具则更省）。
2. `NotificationService.java:466`：`event.title()` → `CredentialStructure.hidePasswords(event.title())`。
3. 保留 `用户=`/`来源=`/`outcome=`/`dedupKey=`/`targetIpMasked=`（对研判有用且非秘密）。

## 4. 影响面（改之前必须确认）

| 关注点 | 评估 | 依据 |
|---|---|---|
| **会不会让 fail2ban 失效** | **不会**。fail2ban 读 srv2 的 **sshd/系统认证日志**，与本应用 `app.log` 无关 | 应用日志是**下游**产物 |
| **会不会让 Wazuh 规则失效** | **不会**。Cowrie 原始日志在 **srv2 由 wazuh-logcollector 采集**，Wazuh 规则在应用**之前**已判定完 | 顺序：Cowrie → srv2 Wazuh → indexer → 应用 |
| **会不会改公开面契约** | 只把 `口令=<值>` 变 `口令=[口令已隐藏]`；`code/message/data` 结构与 `dataSource`/`ipDisclosure` 等**不变** | `/honeypot` 已长期这样输出，是既有契约 |
| **会不会影响 IP 掩码口径** | **不会**。`app.public.mask-ips` 与 `PublicIpPolicy` 逻辑不动 | 两件事正交 |
| **会不会影响通知投递** | **不会**。只改日志/响应文本，`transport.post` 不动 | 改的是 `logger.info` 入参 |
| **审计证据会不会丢** | 保留 `用户=`/`来源=`/`outcome=`/`dedupKey=`，仅口令变 `***`/`[口令已隐藏]` | 仍可复盘"谁试图通知、结果如何" |
| **`/api/public/alerts/{aggId}` 下钻** | **同一缺陷**：`publicAlert(a)` 也会带出 `title` | 改 `scrubDeep` 可一并覆盖；只改 `buildAlerts` 则下钻仍漏 |

> ⚠️ 上表最后一行很重要：`drillDown()`（`PublicApiController.java:367+`）走
> `members.add(publicAlert(a))`，同样只经过 `ship()`。
> **因此推荐 §3.1 的第二种改法（改 `scrubDeep`），它能同时盖住 `/alerts` 与 `/alerts/{aggId}`。**

## 5. 验收与落地顺序

1. **先治 ③**（对外可见且与自述红线冲突），再治 ①②。
2. 验收（缺一不可）：
   - **持续抽样**（至少 60s、间隔 ≤5s）`/api/public/alerts`，`grep -E '口令=[^[]'` **零命中**；
   - `curl -s .../api/public/alerts/<aggId>`（取一个含蜜罐的 aggId）同样零命中；
   - `/api/public/honeypot` 仍稳定 `口令=[口令已隐藏]`；
   - `/api/public/{alerts,webstats,geo}` 仍 **200**，`dataSource` 仍 `REAL`；
   - `/api/health` 仍 `status:ok`、`fingerprintMismatch:false`；
   - 新产生的 `app.log` / `notify-audit.jsonl` **不再出现** `口令=<非***>`；
   - 通知实际投递未下降（看 `NotificationAudit` 的 `outcome=SENT` 计数）。
3. **历史数据**：已落盘的 567/572 处明文**不会**因代码改动消失；
   是否清理历史 `app.log` / `notify-audit.jsonl` 需单独决定（清日志会影响近期排障）。
