# CSRF 跨站请求伪造（CWE-352）

## 一、原理
用户已登录 A 网站并保持会话，当用户访问攻击者构造的 B 网站时，B 页面在用户不知情的情况下向 A 网站发起请求，浏览器会自动带上 A 的 Cookie，从而冒用用户身份执行操作。

## 二、前提条件
- 关键操作仅依赖 Cookie/Session 认证；
- 请求参数可被预测、无随机校验；
- 服务端不校验请求来源。

## 三、典型攻击
- 自动提交的表单（转账、改密、改邮箱）；
- 图片/脚本标签触发 GET 请求；
- JSON 接口通过表单、Flash 或 CORS 误配配合攻击。

## 四、危害
冒用用户身份执行敏感操作（转账、改密、发帖、增删数据），但攻击者通常无法读取响应。

## 五、与 XSS、SSRF 的区别
- CSRF：冒用用户身份**发请求**，不执行脚本；
- XSS：在浏览器执行脚本，能读取响应，能力更强；
- SSRF：由**服务器**发起请求，攻击内网。

## 六、防御
1. **CSRF Token（主流）**：服务端为每个会话/表单生成随机 Token，提交时校验；攻击者无法预知。
2. **SameSite Cookie**：关键 Cookie 设置 `SameSite=Lax`（或 Strict），跨站请求不带 Cookie。
3. **校验 Origin / Referer**：对敏感请求校验来源。
4. **敏感操作二次确认**：二次密码、验证码、重新登录。
5. **改用 JSON 接口**：简单表单无法直接发送跨站 JSON，但仍需 CORS 配合。
6. 对接口开启合理的 CORS 策略，不要用 `Access-Control-Allow-Origin: *` 且允许凭据。

## 七、与项目关联
- 原始项目 CORS 配置为 `*` 且允许凭据，放大了 CSRF/跨站调用风险；改造后收敛为来源白名单（仅本机）。
- 本项目另提供 Token 鉴权（`X-API-Token` 头，而非 Cookie），配合自定义请求头，天然规避了传统表单型 CSRF。
