# 渗透测试报告编写与漏洞复测

> 渗透测试是安全服务工程师的核心交付，报告质量直接体现专业度。本文讲报告结构、漏洞描述规范、风险定级与复测流程。

## 一、报告整体结构
一份规范的渗透测试报告通常包含：
1. **封面与概述**：项目名称、测试时间、测试方、授权范围、报告版本与保密级别。
2. **测试说明**：授权范围（IP/域名/系统）、时间窗口、测试方法、风险与免责声明。
3. **总体评价**：资产数量、发现漏洞统计（按等级/类型分布）、整体安全态势结论。
4. **漏洞详情（主体）**：每个漏洞单独一节。
5. **风险总结与整改建议**：按优先级给出修复路线图。
6. **附录**：测试证据、复现脚本、参考资料。

## 二、单个漏洞的标准写法
每个漏洞建议包含固定字段：
1. **漏洞名称**：如"XX 系统某接口存在 SQL 注入漏洞"。
2. **漏洞编号/类别**：CWE（如 CWE-89）、对应 OWASP Top10。
3. **风险等级**：严重/高/中/低/提示（结合 CVSS 与业务影响）。
4. **影响范围**：受影响 URL、参数、系统、版本。
5. **漏洞描述**：根因（代码/配置缺陷），讲清"为什么会有"。
6. **复现步骤**：编号化、可复现，给出请求示例（截图/请求包）。
7. **危害证明**：以最小证据说明能做什么（如读取表结构、越权看到他人数据），不做过度利用。
8. **修复建议**：具体、可落地（代码级、配置级）。
9. **复测结果**：修复后重新验证的结论。

## 三、风险等级判定（CVSS + 业务影响）
- **严重**：可未授权 RCE、Webshell、拖库、获取系统控制权、核心数据泄露。
- **高危**：越权访问/修改敏感数据、可获取大量凭据、逻辑漏洞造成直接损失。
- **中危**：存储型 XSS、有限信息泄露、需较高条件利用的漏洞。
- **低危**：反射型 XSS、低敏感信息泄露、版本指纹、错误回显。
- **提示**：安全配置建议（Cookie 安全标志、响应头、目录列举等）。

CVSS 参考维度：攻击途径（网络/本地）、攻击复杂度、所需权限、用户交互、机密性/完整性/可用性影响。定级要结合**业务影响**（如涉及资金、个人信息时上调）。

## 四、复现步骤写作要点
- 编号清晰、环境明确（账号、角色、目标、前置条件）；
- 给出关键请求（URL、方法、参数、请求头）与响应差异；
- 用截图/回显作为证据，关键信息打码；
- 只展示"证明漏洞成立"的最小步骤，不展开深度利用、不提供批量利用脚本；
- 对数据类漏洞，不展示真实敏感数据。

## 五、修复建议怎么写才专业
- 讲清楚"正确做法"，给代码/配置示例：
  - SQL 注入：参数化查询/预编译、ORM 的 `#{}`、输入校验；
  - 上传：扩展名白名单、取最后一个点、内容校验、目录不可执行；
  - XSS：输出编码、CSP、HttpOnly；
  - 越权：服务端对象级鉴权（BOLA）；
  - 认证：失败锁定、MFA、强口令；
- 必要时给出"临时缓解"（WAF 规则、下线、限制访问）与"根治方案"（代码/配置）。

## 六、漏洞复测（验证修复）
1. 修复后在**同样条件**下重放原复现步骤；
2. 已修复：原 payload 被拦截/无效，记录复测结果与证据；
3. 未修复/部分修复：说明残留问题（如只在前端校验、黑名单可绕过），退回整改；
4. 检查修复是否引入新问题（如功能异常、规则误杀）；
5. 输出复测结论与最终整改确认表。

## 七、好报告的标准
- 事实准确、可复现、证据充分；
- 风险定级与业务影响相符，不夸大不遗漏；
- 修复建议可落地、可验证；
- 语言专业、结构清晰、保密合规；
- 漏洞描述先讲根因、再讲现象，最后给修复。

## 八、与项目关联
SecAgent 的知识库问答可辅助生成漏洞的"根因说明、危害、防御建议"，多 Agent 研判报告也遵循"告警→证据→攻击链→影响→处置建议"的结构，与渗透报告的逻辑一致；面试时可演示：向助手提问"SQL 注入怎么复现、怎么修复、报告怎么写"，展示其作为安全服务工程师辅助工具的价值。
